# 检测软件合并请求

## 目标

帮助技术负责人按明确意图查看、评审或合并同事提交的 MR。纯查看保持轻量；需要评审或合并时，才执行真实代码评审和快照复核。

## 使用前

先读 [公共说明](../manage-yunxiao-workitems/references/common.md)，统一组织、仓库定位、分页、写入与回读规则。下文使用不带客户端前缀的官方 MCP 工具名称。

MR 列表可能没有状态字段，需要确认状态时用 `get_change_request`。提交人、仓库范围和评审门禁由本技能决定。

用户明确要求关闭指定 MR 时，先读取详情确认对象，再按 [CLI 补充](../manage-yunxiao-workitems/references/cli-supplement.md) 的关闭流程执行；关闭不触发批准或合并，也不因“查看/评审”而自动发生。

## 默认仓库范围

默认只处理以下仓库：

- `syjc-boot`
- `syjc-web`

当用户要求“查看待合并请求”“合并所有请求”“处理全部请求”时，只处理以上仓库，忽略其他仓库的合并请求。

## 用户意图路由

先识别意图，再执行任何 `list_change_request_patch_sets`、Git 拉取、代码评审或合并操作。按下表从上到下匹配最具体的表达，较长表达优先于其中包含的短词：

| 用户表达 | 意图 | 处理范围 | 是否评审 | 是否合并 |
|---|---|---|---|---|
| `查看合并请求`、`查看待合并请求`、`列出合并请求` | 仅查看 | 当前默认仓库范围内全部 opened MR | 否 | 否 |
| `查看及评审合并请求`、`查看并评审合并请求`、`查看和评审合并请求` | 查看并评审 | 当前默认仓库范围内全部 opened MR | 是 | 否 |
| `评审合并请求 <ID>` | 指定评审 | 唯一匹配该 ID 的 opened MR | 是 | 否 |
| `合并所有`、`合并所有请求`、`全部合并` | 合并全部 | 默认仓库范围内全部 opened MR，不限制提交人 | 是 | 评审通过后合并 |
| `合并请求`、`合并待处理请求`，且未出现“所有/全部” | 默认合并 | 默认仓库范围内、提交人在默认白名单中的 opened MR | 是 | 评审通过后合并 |

路由规则：

- “查看合并请求”中的“合并请求”是名词，不代表执行合并。该意图只读取仓库、MR 列表及必要详情，不执行补丁集或代码评审；不得运行 `list_change_request_patch_sets`、`review-branch-changes`、`review_change_request` 或 `merge_change_request`。
- “查看及评审”先按完整短语识别，不得降级成“仅查看”。
- “评审合并请求 2817”中的数字默认匹配 `localId`；若用户同时给出仓库，使用“仓库 + localId”定位。没有匹配时停止并说明；多个仓库出现相同 `localId` 且用户未指定仓库时，列出候选并请用户确认，不得评审多个请求。
- “合并所有”仅放宽**提交人白名单**，不扩大默认仓库范围；它本身就是对默认仓库范围内非白名单提交人的批量合并授权，无需再次询问。
- 用户明确指定默认仓库范围外的仓库时，仍按“默认仓库范围外例外”处理。
- 无法可靠判断用户是要查看、评审还是合并时，采用只读的“仅查看”并说明未执行评审或合并，不猜测破坏性意图。

## 默认可合并提交人

以下同事提交的合并请求，在“默认合并”意图下可以进入代码评审与合并候选：

- 张人文
- 丁琪
- 廖海波
- 彭娜娜

不同意图下的提交人规则：

- 仅查看、查看并评审、指定评审：提交人不限制范围；这些操作不会批准或合并。
- 默认合并：只评审和合并上述白名单提交人的 MR；其他提交人的 MR 列为“非白名单，未处理”，不要评审或合并。
- 合并所有：评审默认仓库范围内所有提交人的 MR；非白名单提交人无需二次确认，代码结论为“可合并”且快照复核通过后直接合并。
- 用户明确指定某个非白名单 MR 执行合并，但没有说“合并所有”时，仍需在批准或合并前二次确认。

提交人白名单只代表默认合并范围，不代表代码质量。任何进入合并候选的 MR 都不能跳过 `review-branch-changes`，也不能用白名单身份或“合并所有”覆盖“不可合并”或“需人工确认”的评审结论。

识别提交人时优先使用合并请求 JSON 中表示提交人或创建人的字段，例如 `creator`、`author`、`createdBy`、`submitter`、`createdByName`、`authorName`，并读取其中的 `name`、`displayName`、`userName`、`username` 或字符串值。不要用评审人、合并人、最后更新人代替提交人。提交人姓名需要与上方名单准确匹配；无法准确匹配时按“非白名单提交人”处理，再根据当前意图决定跳过、评审或等待确认。

## 默认仓库范围外例外

如果用户明确提出默认仓库范围外的仓库或 MR，可以处理。支持两类请求：

- 单独指定某个默认范围外仓库或某个具体 MR。
- 明确要求“合并其他仓库的所有请求”“合并除 `syjc-boot`、`syjc-web` 之外的所有请求”。

必须满足：

- 用户明确指定了仓库、MR ID、标题，或明确要求处理默认仓库范围外的全部请求。
- 单独指定时，只处理用户指定的请求，不要顺带处理同仓库或其他默认范围外请求。
- 明确要求处理默认范围外全部请求时，只处理范围外请求，不要同时处理默认范围内请求，除非用户也明确要求。
- 汇报时说明这是用户明确要求处理的默认仓库范围外请求。

如果用户只是泛泛说“全部合并”“检测所有合并请求”，不要合并默认仓库范围外的请求。

## 与代码评审技能的协作约定

每个进入评审或合并候选的 MR 都必须读取并按 `review-branch-changes` 执行（同目录下未安装时使用 `~/repos/syjc/.agents/skills/review-branch-changes/SKILL.md`；均不可用时停止评审/合并），并传入：

- 本地仓库路径或 `nameWithNamespace` 最后一段得到的仓库名。
- `projectId`（作为 MCP 的 `repositoryId`）、`localId`。
- `sourceBranch`、`targetBranch`。
- `list_change_request_patch_sets` 返回的源、目标最新补丁集：`patchSetBizId`、`commitId`、`ref`。

接收且只接收以下门禁结论：

- `可合并`：代码质量门禁通过，但仍需满足提交人授权和合并前快照复核。
- `不可合并`：不得批准或合并；汇报具体问题和修改建议。
- `需人工确认`：不得自动批准或合并；汇报证据不足或验证受限的原因。

目标分支是仓库默认主分支时，还必须接收以下三项红线状态及证据：

- 主分支专属代码隔离。
- `sdjt/dev` 来源与派生关系隔离。
- `gx-concrete/dev` 来源与派生关系隔离。

三项必须全部为“通过”，整体结论才可能是“可合并”。任一项“命中”时整体结论必须为“不可合并”；任一项缺失或为“需人工确认”时整体结论必须为“需人工确认”。源分支名为 `feature/*`、`bugfix/*` 或其他普通名称不能跳过派生关系检查。

## 操作流程

### 1. 识别意图并获取列表

先按“用户意图路由”确定本次是仅查看、查看并评审、指定评审、默认合并还是合并所有，再获取所有待合并请求：

调用 `list_change_requests`，传 `organizationId`、目标仓库 `projectIds`、`state="opened"`，分页取得完整列表。

根据用户要求筛选仓库范围：

- 默认范围：筛选仓库属于 `syjc-boot`、`syjc-web` 的请求。
- 用户单独指定默认仓库范围外请求：从结果中定位该指定请求。
- 用户明确要求默认仓库范围外全部请求：筛选仓库不属于 `syjc-boot`、`syjc-web` 的请求。

仓库名优先从 `nameWithNamespace` 的最后一个路径段提取；同时保留原值用于汇报。MR 列表中的 `projectId` 是后续 `list_change_request_patch_sets`、`review_change_request` / `merge_change_request` 使用的 `repositoryId`。

### 2. 按意图结束或确定评审候选

- 仅查看：直接输出列表并结束。至少显示仓库、`localId`、标题、提交人、源分支、目标分支和状态；明确说明“仅查看，未执行代码评审或合并”。
- 查看并评审：将筛选后的全部 MR 作为评审候选，完成评审后结束，不执行批准或合并。
- 指定评审：用用户给出的 ID 匹配 `localId`，必要时结合仓库名消歧，只将唯一匹配项作为评审候选；完成评审后结束，不执行批准或合并。
- 默认合并：识别提交人，只将白名单提交人的 MR 作为评审及合并候选；非白名单请求只列出为未处理。
- 合并所有：将默认仓库范围内所有 MR 作为评审及合并候选，不因提交人不在白名单而跳过或要求二次确认。

识别提交人时：

- 默认可合并：提交人是张人文、丁琪、廖海波、彭娜娜。
- 非白名单：提交人不是上述名单成员，或提交人无法确认。
- “合并所有”已构成非白名单提交人的明确授权；其他合并意图不得自动扩大到非白名单提交人。

### 3. 为每个评审候选锁定初始补丁集

调用 `list_change_request_patch_sets(organizationId, repositoryId=projectId, localId)`。

- 分别选择 `relatedMergeItemType` 为 `MERGE_SOURCE`、`MERGE_TARGET` 且 `versionNo` 最大的记录。
- 保存两端的 `patchSetBizId`、`commitId`、`ref`，作为本次评审快照。
- 缺少任一端、记录冲突或字段不完整时，将该 MR 标记为“需人工确认”，不得批准或合并。

### 4. 执行代码评审

- 调用 `review-branch-changes`，传入 MR 元数据和第 3 步的精确补丁集快照。
- 目标分支是默认主分支时，明确要求检查固定受禁来源 `sdjt/dev`、`gx-concrete/dev`，包括基于它们创建或继承其非主分支提交的功能分支；不能只比较 MR 当前源分支名称。
- 必须阅读完整评审结果，记录结论、问题、测试结果、残余风险以及实际评审的两个 `commitId`。
- 面向主分支的评审还必须记录三项红线状态、受禁分支实际 commit、共同祖先、重合 commit 或 patch-id 等来源证据。缺少完整红线检查时，按“需人工确认”处理，不得自行补成“通过”。
- 不能只根据 MR 标题、提交说明、改动文件数量或提交人判断是否安全。
- 若本地仓库无法唯一定位、精确快照无法拉取、关键验证未完成或评审覆盖不足，门禁结论只能是“需人工确认”。

查看并评审、指定评审在完成本步骤后直接汇报并结束。只有默认合并和合并所有继续执行后续步骤。

### 5. 应用合并门禁

- 只有 `review-branch-changes` 明确返回“可合并”时才能继续；“不可合并”和“需人工确认”都必须跳过批准与合并。
- 目标为主分支时，再确认三项红线均明确为“通过”。任一项“命中”“需人工确认”或缺失，都必须跳过批准与合并。
- 默认合并再次确认提交人在白名单中。
- 合并所有不再检查提交人白名单，但仍严格执行代码质量和主分支红线门禁；“合并所有”不能覆盖红线。

### 6. 合并前执行防竞态复核

调用 `get_change_request` 和 `list_change_request_patch_sets`，均传 `organizationId`、`repositoryId=projectId`、`localId`。

必须同时满足：

- MR 仍为 opened，仓库、`localId`、`sourceBranch`、`targetBranch` 与评审时一致。
- 最新源端和目标端的 `patchSetBizId`、`commitId` 均与评审快照一致。
- 代码评审结论仍为“可合并”，当前意图对该提交人的合并授权也仍满足。

如果源端或目标端快照变化，旧评审立即失效；回到第 4 步对新快照重新评审，不得沿用旧结论。若 MR 已关闭、字段变化或无法唯一定位，停止处理该 MR。

### 7. 批准并合并

对每个同时通过代码质量门禁、意图授权门禁和快照复核的请求执行批准并合并，默认删除临时功能源分支，长期分支保留：

1. 调用 `review_change_request`，传 `organizationId/repositoryId/localId`、`reviewOpinion="PASS"`，以及本流程授权的 `reviewComment="代码评审通过，补丁集快照已复核"`；不提交无关草稿评论。
2. 批准后再读 `get_change_request` 和两端补丁集，确认仍是同一快照且满足合并条件。变化时不能沿用旧结论。
3. 调用 `merge_change_request`，显式传 `mergeType="no-fast-forward"`、`removeSourceBranch=true`；用户明确指定其他合并策略时按其要求。源分支若为 `master/release/sdjt/dev/gx-concrete/dev` 等长期分支，保留源分支，不能套用临时功能分支删除规则。
4. 用 `get_change_request` 确认 merged 后才报告已合并；按当前宿主要求关联接手处理的 MR。超时或结果未知时先回读，不自动重复批准或合并。

### 8. 汇报处理结果

- 仅查看：列出待处理请求，明确说明未执行代码评审、批准或合并。
- 查看并评审：列出全部请求及各自代码评审结论，明确说明未执行批准或合并。
- 指定评审：列出指定 MR 的信息、评审结论、问题与验证结果，明确说明未执行批准或合并。
- 已合并请求列表：仓库、合并请求 ID、标题、源/目标分支、已评审的源/目标 commitId。
- 代码评审未通过列表：仓库、合并请求 ID、结论、问题摘要和修改建议。
- 面向主分支的请求：额外列出三项红线状态；命中时列出受禁来源或专属功能证据，需人工确认时列出证据缺口。
- 默认合并跳过的非白名单请求：仓库、合并请求 ID、标题、提交人，说明未评审、未合并。
- 用户明确指定非白名单 MR 合并但尚未确认时：列为等待二次确认。
- 已忽略请求列表：说明因为仓库不在默认范围而忽略。
- 默认仓库范围外请求：说明这是用户明确要求后处理的请求，并列出处理范围。
- 失败或停止原因。

## 意图示例

- 用户：`查看合并请求` → 只运行列表查询并展示结果，不获取补丁集，不评审，不合并。
- 用户：`查看及评审合并请求` → 先展示列表，再逐个评审默认仓库范围内的 MR，不合并。
- 用户：`评审合并请求 2817` → 只定位并评审 `localId = 2817` 的唯一 MR，不合并。
- 用户：`合并请求` → 只把提交人白名单中的 MR 纳入评审；评审通过后合并，非白名单请求不评审、不合并。
- 用户：`合并所有` → 默认仓库范围内所有 MR 都先评审；无论提交人是否在白名单，评审通过且快照一致即可合并。

## 单个 MR 跳过条件

以下情况只跳过当前 MR 的批准与合并，并继续评审其他相互独立的待处理 MR：

- `review-branch-changes` 返回“不可合并”或“需人工确认”。
- 目标为主分支，但任一红线状态不是“通过”或红线证据缺失。
- 评审后 MR 的源端或目标端补丁集、commitId、源/目标分支发生变化，且重新评审尚未完成或失败。
- 无法唯一定位该 MR 的本地仓库，或无法取得、验证其精确补丁集快照。

批量处理中不得因为一个 MR 的代码问题而放弃评审其他 MR；但也不得让其他 MR 的成功结论覆盖当前 MR 的失败状态。

## 停止条件

遇到以下情况必须停止，不要继续处理后续请求，并询问用户：

- API 返回冲突、权限不足、保护分支限制、合并失败。
- 待处理请求的仓库无法确认是否属于默认范围，且用户没有单独明确指定该请求。
- 用户要求和检测到的请求不一致，例如指定请求不存在。
- 用户对默认仓库范围外单个请求的描述无法唯一定位到一个 MR。
- 除“合并所有”外，准备对非白名单提交人的请求执行批准或合并命令，但用户尚未二次确认。
- 命令输出中出现异常状态或错误信息。

## 注意

- MCP 没有 CLI 的 `--yes` 参数；写操作必须满足本技能的用户意图、授权和门禁。
- 合并临时功能分支默认 `removeSourceBranch=true`；长期分支保持 false。
- 不要在“全部合并”这类批量操作中合并 `syjc-boot`、`syjc-web` 之外的任何仓库。
- 只有用户明确指定默认仓库范围外请求或明确要求合并范围外全部请求时，才允许合并默认范围外仓库。
- 提交人白名单只决定“默认合并”的候选范围；“合并所有”明确授权处理默认仓库范围内的非白名单提交人。
- 提交人规则不等于代码评审通过；每个进入评审或合并候选的 MR 都必须经过 `review-branch-changes`。
- `sdjt/dev`、`gx-concrete/dev` 及其派生功能分支不得合入主分支；当前源分支改名不能绕过派生关系检查。
